# @lightstart/server: the features most requests need

Status: agreed; not started.

What Express, Fastify and Hono provide (their installed sources read, and Fastify's official plugins' READMEs), and what bootstrapp writes by hand today that a server library should give it, decided together: what light adds, how each piece attaches, in what order, and what bootstrapp deletes once it is there.

## Principles

1. **Nothing a request does not use costs it.** Every feature attaches in the cheapest of four ways that does its job:

   | Attachment | Costs when unused | For |
   |---|---|---|
   | A `Context` accessor computed on first call (as `c.json()` is) | nothing | reading cookies, the bearer token, forms, `Accept`, same-origin |
   | Route middleware, listed by the routes that want it | nothing on other routes | validation, rate limits, timeouts, auth guards |
   | A plugin's hook, built once by `app.build()` | one call per request | security headers, app-wide rate limits, CSRF over every unsafe method |
   | Generated by a `prepare` step before the build | nothing at runtime | validators and serializers from schemas |

   A plugin's per-request work is prepared at build time: fixed header lists computed once, nothing re-derived per request.
2. **The core stays what it is**: runtime-neutral, importing nothing outside the package, compiled fully statically by scriptc, the same under node, natively, behind `toFetch` and in memory. A feature that needs the platform (hashing, compression) takes it through a small seam an adapter fills, never a `node:` import in the core.
3. **Measured on the hello workload.** Paired, pinned rounds (`benchmarks/server --workload hello-get --cpu`, 5 rounds, medians) before and after each phase:
   - what a route does not use (an accessor not called, middleware not listed) may not move CPU per request beyond noise: the median within 5% of the commit before;
   - a registered plugin runs on every request by design, so its cost per request is measured and written in the README beside it (for example "SecurityHeaders: +0.4 µs"), for an app to weigh before registering it.
4. **Bootstrapp deletes code.** Each feature is done when bootstrapp's copy is gone (the inventory below names the files).
5. **Every feature is tested under node and natively** (the package's test gate), and in memory and behind `toFetch` where it touches the request or the reply.

## The features

### Phase A: reading the request (lazy accessors on `Context`)

**Done.** Natively, medians of paired pinned rounds before and after: hello-get 19.77 → 19.55 µs a request, hello-post 21.82 → 21.36, and with `SameOrigin` registered 19.77 and 21.59: within noise.

- **Cookies.** `c.cookie(name): string | null`, `c.cookies(): Map<string, string>`, parsed once on first call. Writing: `setCookie(reply, name, value, options)` and `clearCookie(reply, name, options)`, helpers beside `json` and `fail` that append to `reply.headers`, so several survive and `Reply` keeps its small API. Defaults: `Path=/`, `HttpOnly`, `SameSite=Lax`, `Secure` when the request came over https (`"auto"`, settled when the app finishes the reply, where the request is known). `maxAge` in seconds. `__Host-`/`__Secure-` prefixes checked. Signed cookies come later, on the hashing seam (Phase C).
- **Bearer token.** `c.bearer(): string | null` from `Authorization: Bearer`. Sessions stay the app's.
- **Same origin.** `c.sameOrigin(): boolean` (no `Origin` and no `Sec-Fetch-Site: cross-site` passes; an `Origin` must match `c.host`, which honours `TrustProxy`). And `new SameOrigin({ methods? })`, a plugin refusing a cross-origin unsafe method with 403 before routing; websocket upgrades included, since they run the hooks.
- **Forms.** `c.form(): Promise<Map<string, string[]>>` for `application/x-www-form-urlencoded`, within `c.limit`. Multipart is Phase D.
- **Negotiation.** `c.accepts(...types): string | null` over `Accept`, with q-values.

### Phase B: shaping the reply (plugins, built once)

**Done.** Natively on hello-get, medians of 7 paired pinned rounds: 14.32 µs a request before, 14.09 after, 14.55 with `SecurityHeaders` registered (load average 6 to 11). The conditional check scans a reply's header names once and lower-cases nothing.

- **Security headers.** `new SecurityHeaders(options)`: `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`, `Cross-Origin-Opener-Policy: same-origin`, `Strict-Transport-Security` only on https replies. CSP and `Permissions-Policy` off unless given, as Hono's are: a default CSP breaks apps silently. The header list is built once; a route opts out with `[noSecurityHeaders]`, a reply's own header wins.
- **Conditional replies.** `reply.etag(tag)` sets the ETag, and when the request's `If-None-Match` matches on a GET or HEAD with a 2xx, the app answers 304 with the ETag and cache headers kept. The check lives where the app finishes a reply and costs one null check on replies with no ETag. `reply.cache(control)` sets `cache-control`. No automatic body hashing in the core (Express does it on every send); an `AutoEtag` plugin hashing bodies can come with the hashing seam.
- **Errors.** `onError` exists. Add `app.mapError(match, status)` or a documented convention for mapping a library's errors (bootstrapp's UNIQUE → 409, constraint → 400) once, and one error body shape everywhere: `{ "error": message }` as today, with `fields` when validation fails.

### Phase C: route policies (middleware; state behind small interfaces)

- **Validation.** `validate({ params?, query?, body? })` as route middleware. It coerces query and params from strings, checks the body, answers 400 `{ error, fields }`, and puts the typed values on the context (`c.get(BODY)`). Schemas are light's model field descriptors (`{ $type: "number" | "boolean" | "string" | "array" | "object", … }`, what bootstrapp's models and `validateRow` use), so one schema serves the database and the HTTP edge. The server carries its own small validator for that shape and imports nothing from light; a test holds the two to the same answers on the same descriptors. Under scriptc it cannot be Ajv (runtime code generation): interpreted first, generated from the same schemas later (Phase E).
- **Rate limits for the app's own keys.** `rateLimit({ window, max, key?, store? })` as route middleware, and the same as an app-wide plugin, meant for what only the app can key: a user, an email, an account, a hashed address on one write. Flood protection per IP in front of everything is the proxy's or the CDN's (below). A store interface (`hit(key, window) → { count, reset }`) with an in-memory default; bootstrapp supplies SQLite and D1 stores. Answers 429 with `Retry-After` and the `RateLimit-*` headers.
- **Timeouts for a handler that hangs.** `timeout(ms)` as route middleware: 504 when the handler has not answered, and `c.signal` aborted so work that listens stops (`AbortController` works natively). Slow clients and idle connections are the proxy's.
- **Hashing seam.** A `Crypto`-like seam (HMAC, SHA-256) that the node adapter fills from `node:crypto` and the fetch adapter from WebCrypto; probe what scriptc lowers. It unlocks signed cookies and `AutoEtag`.

### Phase D: files and larger bodies

- **`Static`**: a `transform(path, bytes)` hook (bootstrapp's dev server strips TS and rewrites the importmap), so the dev server runs on it. `Range` requests only if a project serves media from the app itself.
- **Multipart**: `c.formData()` within limits (`fileSize`, `files`, `parts`); streamed parts only if a project needs uploads larger than the limit.
- **Safe redirects**: `redirect(c, target, { sameOrigin: true })` refusing an absolute target on another origin.

### Phase E: generated at build time

Validators (and, if it pays, JSON serializers) generated from route schemas by a `prepare` step (`LIGHT_NATIVE_COMMAND`), the scriptc-friendly form of what Ajv and fast-json-stringify do at startup. Only after Phase C's interpreted validation shows where the time goes.

## Not in the server

**What belongs in front of it.** The server does what needs the app's knowledge: which routes change state, who the user is, what version the data is at, what the schema says. What needs none of it belongs to the proxy or CDN in front (Caddy, nginx, Cloudflare), which does it better: TLS and HTTP/2 and 3, compression of dynamic replies, flood protection and connection limits per IP, slow-client and idle timeouts, large static files with ranges and caching, and balancing across machines. On Cloudflare's planes Cloudflare is that proxy, and what only an app can send there (security headers, CORS) comes from the app. The README says so, so none of the proxy's work is added here later.


Sessions, JWT, OAuth and user models stay in `@bootstrapp/auth`; the server gives them `c.bearer()`, `c.cookie()` and `reply.cookie()`. Logging stays `AccessLog` and `RequestId`, which exist; bootstrapp adopts them.

## Bootstrapp's migration (after each light phase)

- A: the three `sameOrigin` copies, `cookieValue`, the cookie half of `tokenFrom`, `cookie()`, the example's form parse.
- B: the two ETag blocks; the backend's `failure()` becomes one mapping; Pages and the dev server get the Worker's security headers.
- C: `engine/input.js`, most of `views.js:125-173` and `crud.js`'s parsing onto `validate`; meetup-rio's `perAddress` onto `rateLimit` with a D1 store.
- D: `serve/src/static.ts` onto `Static` with its transform.
- F: the Worker and the plain Pages helpers (below).

### Phase F: bootstrapp's Worker and Pages helpers on `@lightstart/server/fetch`

`packages/cloudflare/workers/api/*` and `framework/endpoints/*` (with the Pages runner and the generated dispatcher that embed them) answer with their own `Response` builders, CORS, security headers and parsing. They move onto an `App` served by `toFetch`, so CORS, `SecurityHeaders`, cookies, `validate` and the error shape have one implementation on every plane: the dev server, the SQLite server, Pages Functions and the Worker. The Worker's CRUD gains the column allowlist Pages' has. Done after A to C, which it consumes; each surface ported with its tests passing before and after, and the deployed Functions bundle checked with `wrangler pages functions build`.

## Decisions

1. **Validation schemas** are light's model field descriptors, validated by the server's own small validator (no import from light).
2. **Cookies are written with helpers**, `setCookie(reply, …)` and `clearCookie(reply, …)`.
3. **Security header defaults** are the safe set above, CSP and `Permissions-Policy` off unless configured.
4. **Bootstrapp's Worker and Pages helpers move to `@lightstart/server/fetch`** in this plan (Phase F).

## Order and gates

A, then B, then C (its probes first), then F, then D; E only on evidence. Each phase: the package's gates (`light-native test`, `coverage`, `typecheck`, `check --all`), the hello-get CPU check of principle 3, README and AGENTS.md updated, then bootstrapp's deletions for that phase as a separate change in bootstrapp.
