# Working on @lightstart/app

What the package is and how to use it: [README.md](README.md). This file is what a change to it has to keep.

## Layout

| Where | What |
|---|---|
| `index.ts` | `defineApp`, `AppConfig` (including the site's `title`, its `locale`/`locales`, how it `prerender`s, its `worker`, its `focusOnNavigate`, its `utilities`, its `url` and its `base`), `PrerenderRenderer`, `StoreConfig`, the `App` and `AppArgs` classes, `AppLifecycle`, and `appBase`/`appUrl` re-exported from `base.ts` |
| `base.ts` | `appBase(config)` (the `url`'s path, or `base`, normalised), `setAppBase` and `appUrl(path)`: the one place the deploy base is read and applied |
| `head.ts` | `pageHead` (with `jsonLd`), `currentHead`, `alternatesOf` and the head shape: the route's title, description and path, its `locale`/`routePath`, the app's languages, the structured data, the app's display title, the computed document title, canonical and absolute image |
| `manifest.ts` | `AppManifest`, `AppModel`, `AppController`, `AppSeeds`: the plain records `.light/app.ts` (or `.js`) exports |
| `stores.ts` | `AdapterType`, `MemoryAdapterType`, `StoreHost`, `registerAdapterType`, `adapterTypeNamed`, `adapterTypesOf`, `schemasOf` and `plan`: each declared store checked against the host's adapter types and the models' `$store`, with no engine store in the page's import graph |

| `web/features.ts` | The seam's shapes: `WebStoresFeature`, `WebTransitionFeature`, `WebTransitionPort`, `WebArgsFeature`, `WebUtilitiesFeature` |
| `web/args.ts` | `queryArgs`: the URL query as the app's arguments, imported only when the app declares `args` |
| `web/local.ts` | `LocalStores`: the stores feature the entry passes when the app does not declare `worker: true`, opening every store on the page through `engine.ts` |
| `web/transitions.ts` | `Transitions`: the view-transition `transition`, the morph (a click or `from` source, the next `[data-morph]` element, a reversed history entry), the default `light-morph` stylesheet, imported only with `transitions: true` |
| `web/utilities.ts` | `Utilities`: the theme's utility-class engine and browser runtime, imported only with `utilities: true` |
| `web/indexeddb.ts` | `IndexedDBAdapterType`, kept apart from the host's DOM pieces so the worker entry can open it |
| `web/test.ts` | `openPage(manifest, { path, args, adapters, stores })`: the web host's root mount, theme, routed links and utility classes over memory stores and a history in memory, and `OpenedPage` (`run`, `root`, `find`, `text`, `shows`, `navigate`, `settle`, `stop`); `openBuilt` and `OpenedBuiltPage` add `reload` and `offline` |
| `web/generate.ts` | The web host's part of the generation: `.light/main.ts` (or `.js`) always passing a stores feature (`LocalStores`, or `WorkerStores` when the app declares `worker: true`), `.light/worker.js` for a worker app, the `registerPwa` import and call for a project on `@lightstart/pwa` with `src/pwa.*`, `.light/sync.ts` (or `.js`) for a project whose sources declare a `sync:`, and `.light/components.ts` (or `.js`) and `.light/components.css` for a project on a package that declares `light.tags` (as `@lightstart/components` does) |
| `web/worker.ts` | `WorkerStores` (the feature the entry passes for `worker: true`, over a factory answering a `Worker` or a `MessagePort`), `WorkerStore` (the run's `RunStore` over rpc), `WorkerConnection` (one rpc client, the relayed `modelChanged` and diagnostics, and the worker it terminates) and the page's `worker` (`request`, `relay`, `mirror`, `serve`, applied to each connection); it configures the page's model request, and the page imports no engine store |
| `web/worker-entry.ts` | `serveModels({ app, models, worker, port })` and `defineWorker`: the worker plans and opens every store with its adapter types, builds the engine store, serves `model`, `store.count`, `store.addMany`, `store.close`, `open` and the project's handlers, relays `modelChanged`, the diagnostics and the project's events, mirrors the project's signals, and runs the project's `opened` |
| `static/index.ts` | `renderApp(manifest, { path, args, adapters })` and `renderPage(manifest, page, options)`: the app's root view rendered on light's markup host over memory stores and a history in memory, with `<app-container>` as a markup view drawing the route's layout and view and `<app-slot>` drawing a slot's items, and that markup put in a built page with the prerender marker |
| `tui/index.ts` | The terminal host: `TuiHost` (with `surface: false` for a mode's run), `ModeContext`, `JsonlAdapterType`, `hostArgs` (`--data`, `--scheme`, `--route`), argv, the history in memory, `<app-container>` as a terminal view, the baked table, `runApp`, `start` |

## Rules the sources keep

- The core names no host. What only one host does (its store adapter types, where its arguments come from, its history, its surface, its generated entry and files) is that host's subpath; the core reaches it through `AppHost` and `HostGeneration`.
- The web host imports no optional feature or engine store: the generated entry imports the stores feature (always: `LocalStores`, or `WorkerStores` for `worker: true`), the IndexedDB adapter type, the transition feature, the utility-class engine and the URL-argument parser only when the config uses them, and passes them to `start`. `start(manifest)` without a stores feature rejects with an error naming the generated entry; without transitions, utilities or arguments it uses the plain defaults. The utility engine starts from the theme the host applies (a preset name or the given object) before the root view draws, and stops when the run stops; with `theme: false` it still starts from the app's theme when one resolves. A store with no adapter means IndexedDB on the web (a non-worker app), and an `adapter` that is a function makes the entry import every web adapter type. An adapter type a declared package ships under `light.adapters` is imported when a store names it, passed to `start`, or registered in the worker before `serveModels`; two packages declaring one name is an error.
- The web host applies the app's `scheme` before the theme: `"dark"` and `"light"` pin the `dark` class on `<html>` and stop following the preference, `"system"` follows as before, and `color-scheme` matches. `renderPage` writes `class="dark"` on a dark app's `<html>`, and `openPage` restores the page's scheme on `stop`.
- A route change applies inside the host's `transition(apply, route)`: the run calls it when `app.transitions` is on or `navigate(path, { transition: true })` asks, passes the route's path, new `href` and `from` source, and the web host wraps it in `document.startViewTransition` where the browser has it and waits for `<app-container>` to draw. Every other host and `openApp` run `apply` as it is. `navigate(path, { transition: false })` runs plainly. The web host morphs the clicked link (its own capture listener) or the `from` element into the next view's first `[data-morph]` element, else the view element, names only one element `morph` at a time, remembers per entry the path a morph forward led to so a history navigation reverses it onto the restored page's link (preferring `data-morph-source`), installs the default `morph` rules in the `light` layer, and sets no name under `prefers-reduced-motion: reduce`.
- One run, the same on every host: arguments, stores, seeds into empty stores, controllers in import order, routes, mount. `stop` is the reverse: unmount, routes, controllers in reverse, stores. `restart` and `quit` are the run's, installed on `app` by every host and by `openApp`; they reject with "the app is not running" before a run.
- `AppHost` is a class whose methods all have a default, not an abstract class; `openStores` is a function property that rejects, and each host that keeps rows sets its own in its constructor: scriptc does not dispatch an override of a promise-returning method the run calls through `AppHost`, and it does call a function property. A method answering a promise is not `async`: scriptc does not dispatch an abstract method's override reliably, nor an async override. An `AdapterType`'s `open` follows the same rule.
- Stores: `main` is always declared, of the host's default adapter unless the app says. A store's adapter must be one the host runs, a project's registered one, or `memory`; a model's `$store` must name a declared store. Both are errors before anything opens. A test opens every store in memory. `defineApp({ worker: true })` opens every store in one web worker, over one engine store there; the page's model apis go through `configureModel({ request })`, and the run gets a `RunStore` proxy.
- A project on `@lightstart/pwa` with `src/pwa.ts` or `src/pwa.js` gets an import of the config and of `registerPwa` from `@lightstart/pwa/page` in `.light/main` (or `.js`), and `registerPwa(config, { base })` once `start` answers. A project with neither file keeps its entry unchanged; one with a file but without the package is a generation error naming `@lightstart/pwa`. `@lightstart/pwa/page` is web-only.
- A `worker: true` app may add `src/worker.ts` or `src/worker.js`, exactly one (both is an error naming both): it default-exports `defineWorker({ serve, relay, mirror, opened })`, imported by `.light/worker.js` before `serveModels` and passed to it. The worker's `serve` and `relay` merge into ONE `serve` and ONE `relay` table beside light's, a name light uses being an error; `mirror` installs each signal with its `owner`; `opened` runs after the stores open and before `open` answers, with the engine store and a request to the page. The page's `worker` records `serve`, `relay`, `mirror` and `request` and applies them on each `WorkerStores` connection, re-installing the merged tables when a declaration arrives after the connection is open. `WorkerStores`'s factory answers a `Worker` or a `MessagePort`; only a `Worker` is terminated on stop. `serveModels` takes an optional `port` for a backend that hands the page a port rather than a dedicated worker.
- The manifest lists the controllers in the order they start: taken by name, each after the controllers it imports for their values (`import type` does not count), read from its relative imports. A cycle is an error that names it.
- A file name is the manifest name: without the extension and unchanged (kebab-case stays). `.ts` and `.js` are read, `.d.ts` and `*.test.*` are not. Generation sorts its input and its output.
- The app module is `src/app.ts` or `src/app.js`, exactly one (both is an error naming both). A `.js` app gets `.light/app.js`, `.light/main.js`, `.light/components.js`, `.light/locales.js` and `.light/sync.js`, with `.js` imports between them and no TypeScript syntax; a terminal app keeps `.ts` generated files.
- `.light/app.ts` uses static imports only: relative from `.light/`, one per file, views side-effect only, the same for every host but `rootView`, which a host that makes the root view (`HostGeneration.rootView`) gets, the core's `.light/locales.ts` (or `.js`) for a project on `@lightstart/i18n`, and the host's own side-effect imports (`HostGeneration.prepare`): those two come right after the app module and before every model, controller and view, since a controller's or a view's `sync:` is checked as its module is defined. A file is rewritten only when its content changes.
- The web host writes `.light/sync.ts` (or `.js`) when any file under `src/`, or the module of a package tag the app uses (written, used or loaded), declares a `sync:`, so the manifest imports it before the views: `View.use(syncPlugin)` always, and `registerSyncBinder(modelBinder)` when a target is a model api imported from `src/models/`. A project with no sync gets no file. `View.use` and `registerSyncBinder` are idempotent, so an app that still calls either itself keeps working.
- A folder with no `src/app.ts` or `src/app.js` is untouched by every entry point: the command, both serve hooks, the build steps and the test extension.
- Icons are CSS masks generated into `.light/icons.css` from the names the app's `src/` and its used component modules carry, and from every `icons/<name>.svg` at the project root, by the app's set `icons` (`"lucide"` by default) and its installed `@iconify-json/<set>`. An app icon is named by its file, sized from its root `viewBox` (then `width`/`height`, then 24), is written whether or not a literal names it, and wins over a set icon of the same name; it is written even when the set is not installed. A dynamic binding is covered when the app names icons anywhere (literals, data fields, `content/` frontmatter, `icons: [...]` or `static icons = [...]`, its own `icons/`); the check reports a binding in an app that names none, an unknown name, an app icon shadowing the set's, a missing collection (unless every drawn name is an app icon), and an icon file whose name or drawing breaks the mask conventions. `lc-icon` warns once on the page for a name no stylesheet draws. The generation writes no file when nothing is drawn or the mask module does not resolve, and a change under `src/` or `icons/` regenerates it.
- The manifest is a plain typed record of arrays, never a `Map` of functions. Controllers cross as `unknown` and are narrowed by the run.
- A package's views are tags the generation defines when the package says `"light": { "tags": "<its table>" }` and the app declares it. The table maps each tag to `module`, `style`, `extends`, `uses` and `loads`; the generation imports `<package>/<module>`, imports styles from `../node_modules/<package>/<style>`, follows bases and uses transitively, and reads icon names from the modules' sources. A tag two packages define is an error naming the tag and both packages. `@lightstart/components` declares its table this way and keeps two of its modules in the generation: `display/icon-mask.js` writes `.light/icons.css`, and `utils/on-demand.js` defines a table's `loads` tags.
- A slot is a `Slot` handle its owning module exports; `defineSlot` refuses a name already defined. `items` holds the items themselves (never copies: scriptc cannot check a spread cast to `Item & {...}`), sorted by `order` then fill order, and `extensionOf` answers who filled one; a `SlotEntry` carries a fill function rather than the slot, since scriptc treats each generic instantiation of `Slot` as its own class.
- Extensions are the manifest's `extensions`, written by the core generation: each dependency declaring `light.extension` (by package name), then `src/extensions/*` (by file name), imported after the app module and the prepared imports and before the models. A dependency's `light.devOnly: true`, or an app's `src/extensions/<name>.dev.ts` (or `.dev.js`), makes one dev-only: `generate` with `dev: false` (a release build) leaves it out, while `light serve`, `light test` and the default include it. A project with none gets no key and unchanged files. The run fills their slots after the seeds and before the app's controllers, starts their controllers after the app's (`startControllerList`), calls `connected` in order, merges their routes before the locale expansion, and on stop calls `disconnected` in reverse, stops their controllers before the app's and withdraws every fill. `defineApp({ extensions: { off } })` and the run's own choice (`openApp`/`openPage` `extensions: false | { off }`) leave extensions out; an unknown `off` name is a warning.
- Routes are the core's on every host: the router's core (`@lightstart/router/core`) over the host's `history()`; `currentView` is the matched leaf's view tag, `currentRoute` the matched route (`{ name, path, params, query, route }`, with the app path and path params only), and both are null once a run stops; `<app-container>` is each host's. `href` and `url` take an app path or a route name with its params and query and put the base before the answer once; `navigate` follows either with the app path, the router adding the base once. The browser adapter and `configureNavigation` stay the web host's.
- A route draws a level from the chain top ancestor to matched leaf (`outlet.ts`, through each config's `parent`). The root container draws level 0 with the route's layout (its own, else `defineApp({ layout })` for a top-level route, none for `layout: null`); a layout's container draws the view of its own level; a routed view's container draws the next level with that route's own layout, the app default not applying below the top. A route with no `view` takes no level and its layout wraps the next view; a container past the chain draws nothing. Each host finds its position from a WeakMap of the elements it made (`{ level, kind }`), never from attributes, and keeps a layout or view element while its tag stays, so a layout's state survives a view change and a view's element survives a parameter change. Route `props` are set as written, a path or query param of the same name winning; a param is converted to the type the view declares for that prop (`T.number()` to a finite number, a boolean for `""`, `"true"`, `"1"` and `"false"`, `"0"`), read from the tag's `properties` on the web and markup hosts. The terminal's props are declared on the instance, so its `$setProp` reads the current value's type.
- The terminal host takes argv with its own `--data` (default `.data`), `--scheme` (default `dark`) and `--route` (default `/`) merged in, an app declaring those names keeping its own; an `ArgError` prints its message and exits 2. Without a TTY it exits 2. Keys go to the root view's `onKey` when it has one, and its `mounted(renderer)` is called once `runApp` answers.
- A mode file exports `main(argv, context)` (answering the exit code) and may export `matches(argv)`. `context` is a `ModeContext` over the manifest and the argv without the mode's `--<name>`; its `open(argv?)` runs the app through `AppRun` on a `TuiHost` with `surface: false` (arguments, stores, seeds, controllers, routes; no mount) and answers the handle that stops it. The terminal generation imports modes with `import * as modeN`, checks the optional export with `Reflect.get` and `typeof` (scriptc rejects a direct optional property read), runs the first match before the host and exits with its code.
- The app is one `App` instance and its arguments are read by name through `AppArgs`: a host writes `app.args.values`, never replaces `app` or casts it to another shape, because scriptc copies a value it converts and the controllers would read the copy. `test/tui-args.test.ts` and `test/routes.test.ts` run natively for that reason.
- A terminal app's code follows light's scriptc rules: erasable TypeScript, classes for identity, no computed imports, no `Map` of functions, and `unknown` narrowed with `typeof`, `instanceof` or `Array.isArray`. Its `package.json` `native.entry` is `.light/main.ts`.
- `openApp` and `mountApp` import no IndexedDB and no node-only module, so both run natively.
- `openPage` and `OpenedPage` are the web host's and the page's DOM, so they run in a browser test.
- `static` renders on light's markup host: a caller imports `@lightstart/light/markup` before the app's manifest, the root view and `<app-container>` are markup-host views, the markup carries the engine's markers, and a root view the markup registry does not know is a clear error. `renderPage` replaces the root placeholder and puts the prerender marker first in `<head>`.
- The deploy base is `appBase(config)`: the `url`'s path, or `base` overriding it (`"/"` is none), reused by the generator's `infoOf`, the run (the router's `basePath`), the web host's link observer, `appUrl`, `light serve` and `light build`. A view writes app paths; only the host adds or strips the base. The canonical is the app's `url` plus the app path, never the base twice. No base leaves generated and built files byte for byte as before.
- The build's static files read the app's `url`, `base` and the routes through the generator's `infoOf` and `routesOf`, never the generated manifest (which imports the views): `404.html` is the built page, the sitemap leaves out a path with a parameter or wildcard, and `_headers` caches the hashed `.js` and `.css` outputs but not the pages, all under the base.
- Languages: `defineApp({ locale, locales })` names the default and the languages it ships, and the default must be among them. With more than one the run expands the routes (`routes.ts`) into a `/<lang>` variant per other language, the same view, layout and props, a variant named `<name>@<lang>`, and passes `locales`/`defaultLocale` to the router core. `href`/`url`/`navigate` read the target in the current route's locale unless `{ locale }` names one; a path already carrying a declared locale and a `localized: false` route stay as written. `currentRoute.locale` is the matched language (the default when bare) and `currentRoute.routePath` the path without its prefix. A route change tells the i18n seam (`onRouteLocale`) its locale in `beforeNavigate`, before the router reads a `t()` title, and again before the views draw; `navigateLocale` follows `setLanguage`. The core imports no i18n; the generated `.light/locales.ts` wires the two.
- The head writes `<link rel="alternate" hreflang>` per locale plus `x-default`, `og:locale`, and `pageHead`'s JSON-LD, in the web host and in `renderPage`, when the app ships more than one locale; the canonical stays the current page. `pathsOf` takes `{ locales, defaultLocale }` and lists each language's concrete paths; the build's sitemap groups them with `xhtml:link` alternates, and the prerender renders each with its language set.
- Prerendering defaults to the markup renderer in `node/prerender.ts`: it imports `@lightstart/light/markup` from the project before its generated `.light/app.ts` (or `.js`), renders each path with `renderPage` one after another, fails naming the path whose render throws, and passes a view's error to the build as a warning with the path. `--renderer browser` (or `defineApp({ prerender: "browser" })`) keeps the Playwright path.
- `.light/` is not committed; the fixture's `.gitignore` names it beside `.deployed/`.
- Tests are plain scripts on `@lightstart/test/assert.ts`, not a test framework. Most are node-only because they walk the disk and spawn the CLI.
- In an app, `light test` sends `*.browser.test.*` (and any file that is neither kind of test, such as `*.e2e.*`) to headless Chromium and every other `*.test.*` to node, with `@lightstart/light/markup` preloaded so the generated manifest's views register; a `*.test.*` file importing `@lightstart/app/web/test` is a `light check` error (`page-test-name`). The partition itself is `node/test-partition.ts` and is unit-tested natively.
- Comments are a JSDoc module header and JSDoc on exported symbols, nothing else.
- TypeScript with erasable syntax only; the package ships its sources and needs no build step.
